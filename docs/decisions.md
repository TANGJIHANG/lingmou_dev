## 2026-09-23 · 首期检测框架暂不定为 MMDetection

- **决定**：第一周竖线（D1–D7）用 torchvision 自带检测模型或 RT-DETR 打通；
  MMDetection / MMRotate **暂缓**，D2–D3 拿到真实数据后重新评估。
- **理由**：
  1. 实测 OpenMMLab 预编译轮子索引：`cu124` / `cu126` / `cu128` 路径**全部 404**，
     可用组合最高只到 **cu121 / torch2.2**（`cu118/torch2.0`、`cu121/torch2.1` 等）。
  2. 本机 RTX 5060 需 **cu128+**（CUDA 12.8 才含 sm_120），已装 torch 2.14.0+cu130，
     与 mmcv 轮子上限差距进一步拉大。
  3. 该索引中 Windows 轮子（`win_amd64`）仅存在于远古版本 `1.1.5/torch1.6`。
     → 在 Windows 上用 MMDetection ≈ **用 MSVC 源码编译 mmcv**，纯消耗且产出仍指向 cu121。
  4. 第一周竖线的价值在**打通链路**（图 → 检测 → ONNX → ORT），不在框架选型。
- **备选与放弃原因**：
  - **MMDetection / MMRotate**（方案原定）：保留为候选，等确定用 Linux/aarch64 环境或
    确认可编译后再启用；旋转框（DOTA/OBB）最终大概率仍需它或等价能力。
  - **PaddleDetection**（Apache-2.0）：无需 mmcv、含旋转框、有 Paddle2ONNX，值得在 D2–D3 一并评估。
  - **Ultralytics YOLO**：**明确排除**。全系 AGPL-3.0 强传染许可，面向企业命题方交付有许可风险。
    （注：学习阶段用它理解检测原理无妨，但不得把其代码与权重带入交付物。）

## 2026-09-23 · 性能基准测试方法固定为 warmup + Event 计时

- **决定**：所有时延测量统一采用 `tools/bench.py` 的方法：
  warmup ≥10 次 → 多迭代 → `torch.cuda.Event` 计时 → `synchronize()` 后取均值。
- **理由**：首版测量未做 warmup，4096³ 矩阵乘测得 **156.8 ms / 2.0×**；
  修正后为 **12.79 ms / 10.5×**，一次性开销被误计入基准，**偏差 7.5 倍**。
  命题核心指标为端到端 ≤200 ms，测量口径错误将导致**全部**性能数据不可信。
- **备选与放弃原因**：
  - `perf_counter` host 侧计时：已弃用。CUDA 异步执行下它测的是**发射**而非**完成**。

## 2026-09-23 · 倍数指标必须同时报告两侧绝对值与运行条件

- **决定**：任何"提速 N 倍"的宣称，必须同时给出分子绝对值、分母绝对值和两者的完整运行条件。
- **理由**：实测中 GPU 绝对性能提升 64%（21.01 → 12.79 ms），但因为 CPU 侧同时被电源模式
  抬快，"倍数"反而从 **11.8× 降到 10.5×**。倍数是个比率，会随基准侧变化而**反向移动**。
  命题要求"综合推理速度相较**传统单节点架构**提升 3 倍以上"，
  若基准定义模糊，评委一句"你们那台对比机器是不是没调好"就能让该指标失效。
- **备选与放弃原因**：只报倍数（不报绝对值）——已否决，不可复现即不可信。

## 2026-09-23 · Windows 训练 + WSL2/Linux 练部署链路

- **决定**：D1–D4 训练在 Windows 本地进行；**D5 起（ONNX → ORT 推理）切到 WSL2 练习**；
  最终上板在 openEuler / 银河麒麟。
- **理由**：
  1. **昇腾 CANN 工具链（含 ATC 转换器）仅有 Linux 版本**，而方案中的降级路线
     `ATC 转 OM + AscendCL` 大概率会被用到（ORT 昇腾后端算子覆盖需实测）。
  2. 板子本身运行 Linux；参赛组别为"国产操作系统软件组"，国产 OS 是答卷的组成部分。
  3. mmcv 预编译轮子只有 manylinux 版本，Linux 下至少"源码编译"这条路是通的。
- **诚实提醒**：WSL2 是 `x86_64 / Ubuntu`，板子是 `aarch64 / openEuler`，**两者不等价**。
  板子上的 `.so` 与 wheel 必须是 aarch64，不能假设"WSL2 能跑 = 板子能跑"。
  → 应尽早对板子做一次 hello-world 级冒烟测试（SSH 登录 + 安装 Python + 跑通一次 ORT CPU 推理）。
- **备选与放弃原因**：全程 Windows —— 否决，ATC 无法运行，等于放弃降级路线。

## 2026-09-25 · 标注以数据集自带原始 GT 为准，弃用第三方 COCO

- **决定**：NWPU VHR-10 的标注用官方 `ground truth/*.txt`，
  社区版 COCO（3921 框）**仅作交叉校验**，不进训练。
- **理由（带实测）**：本仓库解析原始 GT 得 **3896 框**，第三方 COCO 为 **3921 框**，
  相差 0.6%——两个独立来源数量级吻合，说明解析器无系统性错漏。
  但抽查 `001.jpg` 发现坐标不一致：原始 GT 高 **95 px**，COCO 版高 **86 px**。
  二者并非同一套标注，无法解释差异来源，且第三方标注不可追溯。
  按纪律"所有指标都要有口径"，以数据集自带标注为准。
- **备选与放弃原因**：直接用 COCO 省一次解析——否决。
  省下的工作量很小，换来的是"数据来源说不清"，答辩时是负资产。

## 2026-09-25 · 标注解析失败必须报错，不得跳过

- **决定**：`parse_gt_text` / `parse_dota_label` 遇到无法解析的行直接抛
  `DatasetFormatError`，不做"跳过并警告"。
- **理由（带实测）**：NWPU 的 GT 数字是**右对齐**的，形如 `( 108, 60),( 192,154),1`。
  首版正则写死 `\(\d+` 时，实测**静默丢掉 13/650 个标注文件（约 2%）**：

  | 正则 | 解析出的图 | 框数 |
  |---|---|---|
  | 严（不容忍空白） | 637 / 650 | 2485 |
  | 宽（容忍右对齐空格） | **650 / 650** | **3896** |

  跳过坏行只会打一条 warn，批量跑数据时会被日志淹没，最后表现为
  "报告里的数字和别人的对不上，但不知道哪一步丢的"。
  该口径已固化为测试，改动正则会立刻失败。
- **备选与放弃原因**：跳过 + 警告——否决，理由如上。

## 2026-09-25 · 数据获取统一走 hf-mirror，并强制 SHA256 校验

- **决定**：`tools/fetch_datasets.py` 统一从 `hf-mirror.com` 拉取，
  落盘后计算 SHA256 并在 `data/DATA_SOURCES.md` 登记；若清单里已写死哈希则校验不符即失败。
- **理由（带实测网络探测）**：

  - `raw.githubusercontent.com` 请求超时；但 `github.com/<repo>/raw/<branch>/<file>` 可用。

  - SSDD 官方直链是 Google Drive + 百度网盘（提取码 2021）：

- **备选与放弃原因**：直连官方源——不可用；配置代理——本机无代理环境变量，
  且引入代理会让"这份数据怎么来的"多一层不可复现的依赖，不划算。

## 2026-09-25 · 3 类过滤产生"假背景"，D3–D4 训练前必须显式决策

- **决定**：暂以 `configs/datasets.yaml` 的 `drop_emptied: false` 保留现状，

  |---|---|---|---|
  | `false`（当前）| 230 | 150 | **420（含未标注目标）** |

  baseball_diamond 176 ／ ground_track_field 163 ／ tennis_court 108 ／
  airplane 90 ／ basketball_court 86 ／ vehicle 86 ／ bridge 67 ／ ship 57 ／
  storage_tank 28 ／ harbor 27。

  - 换成覆盖率最高的 3 类——暂缓。竖线的价值在打通链路，

## 2026-09-25 · 不为主机代理可用性而关闭 WSL 的网络限制

- **决定**：**保留** Windows 主机的本地代理 `127.0.0.1:7897` 不动；
  WSL 侧走直连（apt 与 PyPI 实测可达）。若将来确需 WSL 访问 GitHub，
  改用 `networkingMode=mirrored`，**而不是关闭代理**。
- **理由（带实测网络矩阵）**：

  | 目标 | WSL 内直连 | Windows 主机 |
  |---|---|---|
  | `archive.ubuntu.com` / `security.ubuntu.com` | ✅ 200 | ✅ |
  | `pypi.org` / `bootstrap.pypa.io` | ✅ 200 | ✅ |
  | `github.com` | ❌ 超时 | ✅（经代理）|

  WSL 在 NAT 模式下访问不到主机的 `127.0.0.1`，启动时明确提示
  *"检测到 localhost 代理配置，但未镜像到 WSL"*。
  但**冒烟测试只依赖 PyPI**，而这条通道本来就是通的——代理不是拦路石。
  反过来，主机访问墙外站点是靠这个代理撑着的，
  **为修 WSL 而关代理，是拿主机的可用性去换一个可选能力，方向反了**。
- **备选与放弃原因**：
  - **关闭主机代理**：否决，损主机且收益仅"WSL 能 clone"一项。
  - **NAT 下把代理指向宿主 IP**（`172.19.176.1:7897`）：否决——
    需代理客户端开"允许局域网连接"，且宿主 IP 每次重启会变，脆弱。
  - **`networkingMode=mirrored`**：保留为按需方案（WSL 2.7.14 支持）。
    未立即启用，因为它要求 `wsl --shutdown` 重启整个 WSL，会打断正在进行的安装。

> **状态更新（2026-09-25 当日稍晚）**：主机代理已关闭（`127.0.0.1:7897` 不再监听，
> `clash-verge` / `verge-mihomo` 进程退出，只剩后台 service）。
> 实测此时**直连 `github.com:443` 反而通了**（此前直连为 `False`、须经代理），
> 因此 `git push` 直接可用，无需任何代理参数。
>
> 两点提醒：
> - 之前"必须走代理"的结论**依赖当时的网络状态**，不是永久事实。
>   网络环境一变（开/关代理、换节点、TUN 模式），结论就要重新实测，不要照抄。
> - **不要把代理写进 git 全局配置**。代理一关，配置还在，推送就会持续失败
>   且报错指向代理、容易被误判为 GitHub 故障。本次未写入全局配置。
>
> 原始判断（"不为了修 WSL 而去关主机代理"）本身仍成立：那是关于**取舍方向**的结论，
> 与"当前代理开还是关"无关。

## 2026-09-25 · ONNX IR version 错配：导出侧必须显式压低

- **决定**：凡本项目产出的 ONNX，都必须显式设置 `ir_version` 不高于目标 onnxruntime 上限；
  `tools/backend_smoke.py` 固定为 **8**（opset 13 要求 IR ≥ 7），并加测试钉住。
- **理由（带实测报错原文）**：

  ```
  onnx        1.23.0   默认写出 ir_version = 14
  onnxruntime 1.23.2   最高支持            = 11
  -> [ONNXRuntimeError] FAIL : Load model failed:
     Unsupported model IR version: 14, max supported IR version: 11
  ```

  `onnx` 与 `onnxruntime` 是两个**独立发版**的包，IR 版本上限并不同步。
  这正是 **D5（导出）→ D6（推理）** 最典型的卡点，而且会在**换环境时突然冒出来**：
  本机 Windows 是 onnxruntime 1.23.2，WSL 里是 **1.30.0**，两者支持的 IR 上限并不相同。

## 2026-09-25 · 基线检测器选 FCOS + ResNet50-FPN（COCO 预训练）

- **决定**：D3–D4 基线用 ``torchvision`` 的 **FCOS / ResNet50-FPN**，
  加载 COCO 预训练权重、替换检测头为 3 类。
- **理由**：
  1. **无锚框**：后处理只有"解码 + NMS"，没有 anchor 尺寸/长宽比这类需要解释的
     魔法数字。D6 要求"逐框与 PyTorch 对齐"，后处理越简单，
     两侧不一致的来源就越少——差异只可能来自模型本身。
  2. **无 RoIAlign / 两阶段结构**：Faster R-CNN 的 RoIAlign 与 RPN 在 ONNX 导出
     和国产芯片算子支持上都是已知难点。FCOS 是单阶段纯卷积，算子面窄得多。
  3. **许可干净**：torchvision 是 BSD-3，满足"不引入 Ultralytics（AGPL-3.0）"的硬约束。
  4. **必须用预训练**：3 类子集只有 230 张正样本，从零训练不可能收敛。
  实测模型规模：**32.1 M 参数**（可训练 31.8 M）——这是 D8+ 压缩率的**分母**。
- **已知部署风险（留给 D5 验证）**：FCOS 检测头使用 ``GroupNorm``。
  部分推理后端对 GroupNorm 的支持不如 BatchNorm 普遍，**昇腾 CANN 上的算子覆盖必须实测**。
  若不支持，退路是：① 导出前融合/替换 GroupNorm；② 换 RetinaNet（头是 Conv+ReLU，
  本仓库 ``engine/model.py`` 已支持切换）。
  这正是"为部署而设计"的落点，不是杞人忧天。
- **备选与放弃原因**：
  - **Faster R-CNN**：精度通常更好，但两阶段 + RoIAlign 对 D5/D6 是额外风险。保留为候选。
  - **RetinaNet**：算子最保守（头是 Conv+ReLU），若 CANN 不支持 GroupNorm 就切它。
  - **SSD / SSDLite**：最轻，但 torchvision 的 SSD 前向里后处理耦合较深，导出更麻烦。
  - **自研网络**：可控性最高，但 D3–D4 的目标是打通链路而非刷精度，不划算。

## 2026-09-25 · `num_classes` 口径：torchvision 要"含背景"，且它自己的文档自相矛盾

- **决定**：``build_detector(name, num_classes)`` 的 ``num_classes`` 一律指
  **前景类别数**，由本函数在内部 ``+1`` 转成 torchvision 要的含背景口径；
  调用方不要自己加。
- **理由（带实测报错）**：本项目实际踩到，症状极具误导性：

  ```
  CUDA error: device-side assert triggered
  aten/src/ATen/native/cuda/IndexKernel.cu:111:
      Assertion `-sizes[i] <= index && index < sizes[i]` failed
  # 报错栈指向 fcos.py:98  generalized_box_iou_loss(pred_boxes[foreground_mask], ...)
  ```

  报错位置（GIoU loss）**离真正原因很远**。真因在 fcos.py:90::

      gt_classes_targets = torch.zeros_like(cls_logits)   # 最后一维 = num_classes
      gt_classes_targets[foreground_mask, gt_classes[foreground_mask]] = 1.0

  FCOS 把**标签值直接当作分类头最后一维的下标**。标签是 1/2/3，
  而 ``num_classes`` 传了 3 → ``[..., 3]`` 在长度为 3 的维度上越界。

  而 torchvision 的两处 docstring **互相矛盾**，正是这个坑难查的原因：

  | 位置 | 原文 | 含义 |
  |---|---|---|
  | ``fcos_resnet50_fpn`` | "number of output classes of the model (**including the background**)" | 含背景 |
  | ``FCOSClassificationHead`` | "number of classes to be predicted" | 不提背景 |

  正确口径是**含背景**（COCO 用 91 = 80 + 1）。本仓库改为在
  ``build_detector`` 内部统一 ``+1``，并用**真实前向**测试钉死
  （``tests/test_engine.py::test_detector_forward_accepts_labels_starting_at_one``）。
- **备选与放弃原因**：让每个调用点自己 ``+1``——否决，等于每个调用点都有一次错的机会。

## 2026-09-25 · D5 导出切面：只导出 backbone+FPN+head，后处理留在图外

- **决定**：导出的 ``.onnx`` **只含模型前半段**，输出三个原始张量
  （``cls_logits`` / ``bbox_regression`` / ``bbox_ctrness``）；
  anchor 生成、解码、centerness、NMS **全部留在图外**。
- **理由**：torchvision 检测模型的 ``forward`` 返回 ``List[Dict[str, Tensor]]``
  ——每张图一个 dict，含 boxes/scores/labels。这是 **Python 对象**，
  既有变长输出、又嵌着 NMS 这类自定义逻辑，**根本无法直接 trace 成计算图**。
  切在模型与后处理之间是唯一可行的方案，而且带来一个决定性好处：

  > D6 要求"逐框与 PyTorch 对齐"。两侧**共用同一套后处理代码**后，
  > 差异就只可能来自模型图本身，而不是"NMS 在两边实现得不一样"这类噪声。
  > **先排除后处理变量，再谈精度对齐。**

- **⚠️ 代价（必须记账）**：产物**不是**"喂图片直接吐框"的成品。
  谁要用它就得自己实现后处理；终态（真上板）必须把后处理也做进去，
  或重写一份无 torch 依赖的实现——那是 D6/D7 的事。
  报告里若把它写成"检测模型已部署"，就是**不实陈述**。
- **备选与放弃原因**：
  - **连后处理一起导出**：否决。torchvision 的 ``batched_nms`` 无法直接导出，
    需引入 ``NonMaxSuppression`` 自定义算子或自写；且会把后处理差异混进 D6 的对齐结果里。
  - **导出成 ``List[Dict]``**：不可行，ONNX 图不能有 Python 对象输出。

## 2026-09-25 · D5 导出规格：opset 17 / IR 8 / 动态 H/W

- **决定**：``opset=17``、``ir_version=8``、**H/W 动态**；导出后强制压低 IR version。
- **理由（带实测）**：
  1. **IR 必须压**。``onnx`` 与 ``onnxruntime`` 独立发版、上限不同步：
     实测 onnx 1.23 默认写 **IR 14**，而 onnxruntime 1.23.2 只支持到 **11**，
     报 ``Unsupported model IR version``。压到 8 是为了能在**板子上可能更旧的**
     onnxruntime 上加载。该步骤写在 ``export.py::_force_ir_version`` 里，
     **每次导出都执行**，不靠"我记得手动改过"。
  2. **动态 H/W 实测成立**。torchvision 的 transform 按**每张图的宽高比**决定缩放后的尺寸，
     所以固定尺寸导出会逼我们改预处理，进而与训练时的预处理不一致。
     实测动态轴在 **32×32 ~ 600×800 全区间**与 PyTorch 一致。
     下表由 ``scripts/export_onnx.py`` 直接产出，**探针输入按固定种子生成，故可逐位复现**：

     | 输入 | 与 PyTorch 最大绝对差 |
     |---|---|
     | 600×800 | 8.583e-06 |
     | 448×640 | 6.676e-06 |
     | 192×256 | 4.292e-06 |
     | 128×128 | 5.245e-06 |
     | 64×64 | 5.245e-06 |
     | **32×32** | 6.676e-06 |

     三个比"对得上"更强的结论：
     - **误差不随尺寸缩小而增大**，始终在 ~4e-06 ~ ~9e-06 的窄带内
       → 图在跨尺寸上是**数值稳定**的，不是"勉强对上"。
     - 特征图最小边在 128×128 及以下降到 **1**，仍成立 → 那条 ``TracerWarning``
       （FPN 的 ``interpolate`` 里 ``if size_prods == 1:`` 被当常量固化）
       **在本任务范围内已被证伪为无害**。
     - **探针必须固定种子**。首版用裸 ``torch.rand()``，导致"最大绝对差"一列逐次漂移
       （实测 600x800 在 8.58e-06 ~ 1.05e-05 之间浮动）。结论虽不变，
       但**文档里的具体数字无法复现**，违反"所有指标都要有口径"。
       现按尺寸绑定独立种子（增删某一行不影响其它行），已实测两次运行逐位一致。

     ⚠️ **口径提醒**：32×32 是**"已测过的最小值"，不是"下限"**。
     实验里没有出现失败点，就不能声称找到了边界。
     若继续下探，预期失败会来自**架构**而非导出：
     ResNet 总下采样倍率 32（conv1 × maxpool × layer2/3/4 各 stride 2），
     输入 32×32 时最后一层特征图恰好 1×1，16×16 应降至 0×0 而报错——
     **那属于 backbone 的架构硬下限，与动态轴无关**，且 32×32 以下对检测已无实际意义。

  3. **推理结果**：导出的图在上述尺寸上与 PyTorch 原始输出最大差 **8.58e-06**，
     通过 ``onnx.checker.check_model(full_check=True)``（含形状推断），
     onnxruntime 1.23.2 可加载。产物 128.6 MB、1040 节点 / 1492 条边、17 种算子。
- **备选与放弃原因**：
  - **固定尺寸导出**：否决。会改变预处理口径，D6 的对齐将失去意义。
    保留 ``--fixed-hw`` 参数以备某些后端/工具链只吃定尺寸图。
  - **追新 opset**：否决。板卡后端往往滞后，opset 17 已覆盖 FCOS 全部算子。
  - **装 ``onnxscript`` 用新的 dynamo 导出器**：暂时否决，见下条。

## 2026-09-25 · D5 导出器：暂用 legacy（dynamo=False），并登记其废弃风险

- **决定**：``torch.onnx.export(..., dynamo=False)``，**使用 TorchScript 老导出器**。
- **理由（带实测）**：本机 torch 2.14 的 ``torch.onnx.export`` **默认 ``dynamo=True``**，
  而它依赖 ``onnxscript``——**本环境未安装**，不显式传 ``dynamo=False`` 会直接失败。
  老导出器无需额外依赖，且对 torchvision 检测模型久经验证。
- **⚠️ 已登记的废弃风险**：导出时 torch 发出明确警告——
  *"Starting in PyTorch 2.9, the new torch.export-based ONNX exporter has become the default."*
  意味着这条路径**将来会被移除**。因此：
  - 报告里不要写"这条导出链路长期稳定"；
  - 一旦需要升级 torch，**第一件事就是重新验证导出**，而不是假定它照旧能用。
  - 届时的迁移路径是装 ``onnxscript`` 并改用 dynamo 导出器，同时重跑本节全部尺寸验证。
- **备选与放弃原因**：现在就地装 ``onnxscript`` 换 dynamo——否决，属无谓风险：
  当前路径已通过全部验收，且换导出器要重跑所有验证。

## 2026-09-25 · D5 附带产出：FCOS 的 GroupNorm 具体导出成 InstanceNormalization

## 2026-09-25 · ONNX 导出可复现，训练不可复现（登记表该怎么用，取决于这一点）

- **决定**：`artifacts/README.md` 的哈希登记表按**两种语义**使用——
  `.onnx` 的哈希可用于**核对"是不是同一次导出"**；`.pth` 的哈希只用于**证明"确实产出过"**。
- **理由（带实测）**：
  - **导出是字节级可复现的**。同一份权重连续导出两次，两个文件 SHA256 **完全相同**
    （`8a8f5b36fd9deb2bdc6fba6c6945b9e52ac73562fb5def8c82e4529a8386a58a`），
    且等于登记表里 `model.onnx` 的值。
    原因：导出只读权重，`torch.rand` 那个 dummy 输入只用于 trace、不进产物，
    常量折叠也是确定性的。
  - **训练不是**。未固定随机种子（且 cuDNN 算法选择带随机性），
    重跑同一份配置得到的是**另一组权重**，SHA256 必然不同。
  - 因此：**`model.onnx` 随时可重建**（一条命令，1–2 分钟）；
    **`best.pth` 丢了就永远拿不回来**——重训不出同一个文件。
- **由此得出的产物保管策略**：
  - `best.pth` 是**唯一不可重建**的产物 → **必须单独备份**（共享盘 / Release 附件）。
  - `.onnx`、曲线图、预测图都可重建 → 不必备份，丢了重跑即可。
  - 这也解释了为什么它们都不进 Git：进 Git 的是**配方**（代码 + 配置 + 数据来源 + 哈希），
    而不是产物本身。
- **⚠️ 一个必须防的误用**：不要把 `.pth` 的哈希当成"可复现性证明"。
  它只能证明文件没被篡改，**不能**证明"换个环境重跑能得到同样结果"。
  报告里若这么写，是**过度声明**。
- **备选与放弃原因**：
  - **为训练也固定种子以求可复现**：保留为待办，现已升级为
    **`docs/roadmap.md` 硬约束 7**（D8+ 一切消融实验的前置），并附落地要点与验证方法。
    代价是打开 `cudnn.deterministic` 会变慢，属"可复现 vs 跑得快"的取舍，
    需单独决策并记录，不能顺手改掉。
  - **只登记不区分语义**：否决。哈希表看不出用途时，
    最容易被当成"这次结果能复现"的证据。

## 2026-09-25 · 消融实测：`drop_emptied` true vs false —— **结论不决定性**

- **怎么评的**：`scripts/eval.py`，同一套 IoU≥0.5 贪心匹配。两组的**数据集规格不同**
  （380 vs 800），所以先做了污染核查：

  | | 评测图出现在其训练集里的比例 |
  |---|---|
  | A (`drop_emptied=true`) | 0 / 76（0.0%）|
  | B (`drop_emptied=false`) | **48 / 76（63.2%）** ← 主评测集偏向它 |

  因此同时报两个集合：**主评测集**（76 张，偏向 B）与
  **干净子集**（28 张，双方都没训过，公平）。

- **实测（置信度阈值 0.5）**：

  | 集合 | 模型 | 召回 | 精度 | 背景虚警框数 |
  |---|---|---|---|---|
  | 主 76 张 | A | **0.978** | 0.949 | **0** |
  | 主 76 张 | B | 0.969 | 0.951 | **7** |
  | 净 28 张 | A | **0.969** | 0.992 | **0** |
  | 净 28 张 | B | 0.962 | 0.992 | **4** |

  各阈值全量：主集 @0.3 A/B = 0.984/0.978、虚警 10/10；@0.7 = 0.956/0.956、虚警 0/2。
  净集 @0.3 = 0.977/0.962、虚警 3/5；@0.7 = 0.954/0.954、虚警 0/1。
  各类别召回（主集 @0.5）：airplane 227/228 vs 226/228；**ship 23/26 vs 21/26**；vehicle 64/67 vs 64/67。

- **观察**：**A 在全部 6 组对比中召回都不低于 B，虚警 5 组更低、1 组持平，无一项落后。**
  但差异很小——召回差 3 框/321（主集）、1 框/131（净集），落在噪声内；
  精度基本持平。**唯一有量的差异是背景虚警**（阈值 0.5 与 0.7 上 A 为 0，B 为 7/2 与 4/1）。

- **⚠️ 限制一（决定性）：n=1，且训练未固定种子，无法排除"这只是两次随机训练的差异"。**
  两组各只跑了一次，而训练**不可复现**（未固定种子、cuDNN 非确定性）。
  所以"训练数据不同"与"随机初始化/算法选择不同"**混在一起，无法分离**。
  → **本次实验不能用来验证那个决策。**

- **⚠️ 限制二：观测到的机制与原先假设**相反**。**
  原假设是"假背景会压低召回"（即过度抑制）。实测**召回几乎无差**，
  差异出现在**虚警**上——即多喂 420 张"含非目标类的图"后，
  模型在**真背景图**上更容易开火。这与"更多负样本应当减少虚警"的直觉也相反，
  原因未明，可能是分布偏移、也可能是随机性。**不要为它编一个解释。**

- **决定**：**暂时维持 `drop_emptied: true`**，但必须标注状态为
  **"未经受控实验验证，原始论证已被证伪（见上文更正）"**。
  维持的理由仅是"没有任何指标比 `false` 差，且训练量减半"，
  **不是**"实验证明了它更好"。

- **下一步（决定性实验，成本很低）**：**用同一份配置重复训练一次**（不加任何参数，
  自动得到不同随机种子），得到 A2，然后比较 **A vs A2** 的虚警。
  - 若 A 与 A2 差异和 A 与 B 相当 → **run-to-run 方差就解释了一切，本消融在当前设计下无效**；
  - 若 A2 ≈ A（虚警同样为 0）→ 数据的影响是真实的，B 的虚警可归因于那 420 张。

  这比"再跑一次 B"更有信息量：它**直接测量**了我们要排除的那个方差来源。

- **备选与放弃原因**：
  - **直接下结论"true 更好"** —— 否决。n=1 的差异无法与随机性区分，写进报告是过度声明。
  - **就此改回 `false`** —— 否决。没有任何指标支持它。

### 决定性实验的结果（同日稍后）：测出了随机性有多大

按上面的"下一步"跑了一次**完全相同配置**的重复训练（`artifacts/train_baseline_repeat`），
记作 **A2**。它用的是同一份数据、同一个配置，**唯一区别是随机种子不同**
（训练未固定种子，故重跑即换种子）。

**污染核查**：A 0/76、A2 0/76（权重内已自记录 `dataset_spec`）、B 48/76。

| 集合 / 阈值 | A 召回 | A2 召回 | B 召回 | A 虚警图 | A2 虚警图 | B 虚警图 |
|---|---|---|---|---|---|---|
| 主 76 张 @0.5（31 背景图）| **0.978** | 0.972 | 0.969 | 0 / 31 | **1 / 31** | **5 / 31** |
| 主 76 张 @0.7 | 0.956 | 0.956 | 0.956 | 0 / 31 | 1 / 31 | 2 / 31 |
| 净 28 张 @0.5（15 背景图）| 0.969 | 0.954 | 0.962 | 0 / 15 | 1 / 15 | 2 / 15 |
| 净 28 张 @0.7 | 0.954 | 0.947 | 0.954 | 0 / 15 | 1 / 15 | 1 / 15 |

命中框数（主 @0.5）：**A 314 / A2 312 / B 311**。

- **结论一：召回无法区分两种条件。**
  `A − A2 = 2` 框（同数据换种子），`A − B = 3` 框（换数据集）——
  **随机性造成的差异与数据造成的差异同量级**。
  → 上次"召回 A 更高"的观察**必须撤回**，它落在噪声内。
  精度同理（主 @0.5：A 0.949 / A2 0.940 / B 0.951，A2 最差）。

- **结论二：背景虚警上，B 超出了随机性下限——但只在一个档位。**
  A2 在**四次评测里稳定为 1 张图**，A 稳定为 0 → **run-to-run 的虚警方差下限约 1 张图**。
  B 在主集 @0.5 上是 **5 张图**（超下限 4 张）；主集 @0.7 是 2 张。
  **而主集是偏向 B 的（B 见过 63.2%），B 仍高出这么多，属保守证据。**
  但净集上 B 是 2 图 vs A2 的 1 图，只差 1 张，**落在噪声里**。
  → **弱证据：方向一致，但只有一档明确超出噪声，不足以定论。**

- **旁证：训练方差本身就很大。** A 的 val 末值 0.6278 vs A2 的 0.6652（差 6%），
  epoch 0 的 train loss 2.7300 vs 2.1054，轨迹明显不同。

- **⚠️ 由此得出的一条比结论更重要的元结论**：**训练不可复现是"这类消融做了也白做"的根因。**
  在固定种子之前，任何单次配对的消融都无法与 run-to-run 方差区分——
  本节就是活生生的例子：**召回上的差异全部是噪声，只有一项侥幸超出下限。**
  因此 **`docs/roadmap.md` 的硬约束 7（固定种子 + deterministic）不是可选项，
  而是 D8+ 一切消融实验的前置**。
  D8+ 计划里有结构化剪枝、INT8 量化、蒸馏、结构重构——每一项都需要消融记录，
  不先把可复现性做掉，那些记录都会是不可解读的。

- **最终决定**：**维持 `drop_emptied: true`，状态标注为"证据弱、未经充分验证"。**
  维持理由：① 没有任何指标比 `false` 差；② 训练量减半（380 vs 800）；
  ③ 虚警上有一项超出噪声下限（弱证据）。
  **不声称"实验证明它更好"**。也**不再为此追加算力**——
  这属于工程纪律层面的记录，不是命题指标；先把 D6 竖线收口做完。
  若 D8+ 数据选型时仍关心此问题，应在固定种子后做**多种子重复**（每条件 ≥3 次）。
