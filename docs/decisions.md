## 2026-09-23 · 首期检测框架暂不定为 MMDetection

- **决定**：第一周竖线（D1–D7）用 torchvision 自带检测模型或 RT-DETR 打通；
  MMDetection / MMRotate **暂缓**，D2–D3 拿到真实数据后重新评估。
- **理由**：
  1. 实测 OpenMMLab 预编译轮子索引：`cu124` / `cu126` / `cu128` 路径**全部 404**，
     可用组合最高只到 **cu121 / torch2.2**（`cu118/torch2.0`、`cu121/torch2.1` 等）。
  2. 本机 RTX 5060 需 **cu128+**（CUDA 12.8 才含 sm_120），已装 torch 2.14.0+cu130，
     与 mmcv 轮子上限差距进一步拉大。
  3. 该索引中 Windows 轮子（`win_amd64`）仅存在于远古版本 `1.1.5/torch1.6`。
     → 在 Windows 上用 MMDetection ≈ **用 MSVC 源码编译 mmcv**，纯消耗且产出仍指向 cu121。
  4. 第一周竖线的价值在**打通链路**（图 → 检测 → ONNX → ORT），不在框架选型。
- **备选与放弃原因**：
  - **MMDetection / MMRotate**（方案原定）：保留为候选，等确定用 Linux/aarch64 环境或
    确认可编译后再启用；旋转框（DOTA/OBB）最终大概率仍需它或等价能力。
  - **PaddleDetection**（Apache-2.0）：无需 mmcv、含旋转框、有 Paddle2ONNX，值得在 D2–D3 一并评估。
  - **Ultralytics YOLO**：**明确排除**。全系 AGPL-3.0 强传染许可，面向企业命题方交付有许可风险。
    （注：学习阶段用它理解检测原理无妨，但不得把其代码与权重带入交付物。）

## 2026-09-23 · 性能基准测试方法固定为 warmup + Event 计时

- **决定**：所有时延测量统一采用 `tools/bench.py` 的方法：
  warmup ≥10 次 → 多迭代 → `torch.cuda.Event` 计时 → `synchronize()` 后取均值。
- **理由**：首版测量未做 warmup，4096³ 矩阵乘测得 **156.8 ms / 2.0×**；
  修正后为 **12.79 ms / 10.5×**，一次性开销被误计入基准，**偏差 7.5 倍**。
  命题核心指标为端到端 ≤200 ms，测量口径错误将导致**全部**性能数据不可信。
- **备选与放弃原因**：
  - `perf_counter` host 侧计时：已弃用。CUDA 异步执行下它测的是**发射**而非**完成**。

## 2026-09-23 · 倍数指标必须同时报告两侧绝对值与运行条件

- **决定**：任何"提速 N 倍"的宣称，必须同时给出分子绝对值、分母绝对值和两者的完整运行条件。
- **理由**：实测中 GPU 绝对性能提升 64%（21.01 → 12.79 ms），但因为 CPU 侧同时被电源模式
  抬快，"倍数"反而从 **11.8× 降到 10.5×**。倍数是个比率，会随基准侧变化而**反向移动**。
  命题要求"综合推理速度相较**传统单节点架构**提升 3 倍以上"，
  若基准定义模糊，评委一句"你们那台对比机器是不是没调好"就能让该指标失效。
- **备选与放弃原因**：只报倍数（不报绝对值）——已否决，不可复现即不可信。

## 2026-09-23 · Windows 训练 + WSL2/Linux 练部署链路

- **决定**：D1–D4 训练在 Windows 本地进行；**D5 起（ONNX → ORT 推理）切到 WSL2 练习**；
  最终上板在 openEuler / 银河麒麟。
- **理由**：
  1. **昇腾 CANN 工具链（含 ATC 转换器）仅有 Linux 版本**，而方案中的降级路线
     `ATC 转 OM + AscendCL` 大概率会被用到（ORT 昇腾后端算子覆盖需实测）。
  2. 板子本身运行 Linux；参赛组别为"国产操作系统软件组"，国产 OS 是答卷的组成部分。
  3. mmcv 预编译轮子只有 manylinux 版本，Linux 下至少"源码编译"这条路是通的。
- **诚实提醒**：WSL2 是 `x86_64 / Ubuntu`，板子是 `aarch64 / openEuler`，**两者不等价**。
  板子上的 `.so` 与 wheel 必须是 aarch64，不能假设"WSL2 能跑 = 板子能跑"。
  → 应尽早对板子做一次 hello-world 级冒烟测试（SSH 登录 + 安装 Python + 跑通一次 ORT CPU 推理）。
- **备选与放弃原因**：全程 Windows —— 否决，ATC 无法运行，等于放弃降级路线。

## 2026-09-25 · D2 数据集选型：NWPU VHR-10（光学）+ SSDD（SAR）

- **决定**：竖线阶段用两个源——光学取 **NWPU VHR-10** 的 3 类子集

     命题"≥2 类数据源统一接入"当天就有可运行的代码支撑。
- **实测代价（必须记账）**：3 类只覆盖 **230/650** 张正样本（35.4%），
  其余 420 张被滤空。详见下面那条"假背景"决策。
- **备选与放弃原因**：
  - **DOTA-v1.5**：roadmap 硬约束"不碰 DOTA 全量"；且本次检索中

## 2026-09-25 · 标注以数据集自带原始 GT 为准，弃用第三方 COCO

- **决定**：NWPU VHR-10 的标注用官方 `ground truth/*.txt`，
  社区版 COCO（3921 框）**仅作交叉校验**，不进训练。
- **理由（带实测）**：本仓库解析原始 GT 得 **3896 框**，第三方 COCO 为 **3921 框**，
  相差 0.6%——两个独立来源数量级吻合，说明解析器无系统性错漏。
  但抽查 `001.jpg` 发现坐标不一致：原始 GT 高 **95 px**，COCO 版高 **86 px**。
  二者并非同一套标注，无法解释差异来源，且第三方标注不可追溯。
  按纪律"所有指标都要有口径"，以数据集自带标注为准。
- **备选与放弃原因**：直接用 COCO 省一次解析——否决。
  省下的工作量很小，换来的是"数据来源说不清"，答辩时是负资产。

## 2026-09-25 · 标注解析失败必须报错，不得跳过

- **决定**：`parse_gt_text` / `parse_dota_label` 遇到无法解析的行直接抛
  `DatasetFormatError`，不做"跳过并警告"。
- **理由（带实测）**：NWPU 的 GT 数字是**右对齐**的，形如 `( 108, 60),( 192,154),1`。
  首版正则写死 `\(\d+` 时，实测**静默丢掉 13/650 个标注文件（约 2%）**：

  | 正则 | 解析出的图 | 框数 |
  |---|---|---|
  | 严（不容忍空白） | 637 / 650 | 2485 |
  | 宽（容忍右对齐空格） | **650 / 650** | **3896** |

  跳过坏行只会打一条 warn，批量跑数据时会被日志淹没，最后表现为
  "报告里的数字和别人的对不上，但不知道哪一步丢的"。
  该口径已固化为测试，改动正则会立刻失败。
- **备选与放弃原因**：跳过 + 警告——否决，理由如上。

## 2026-09-25 · 数据获取统一走 hf-mirror，并强制 SHA256 校验

- **决定**：`tools/fetch_datasets.py` 统一从 `hf-mirror.com` 拉取，
  落盘后计算 SHA256 并在 `data/DATA_SOURCES.md` 登记；若清单里已写死哈希则校验不符即失败。

  且引入代理会让"这份数据怎么来的"多一层不可复现的依赖，不划算。

## 2026-09-25 · 3 类过滤产生"假背景"，D3–D4 训练前必须显式决策

- **决定**：暂以 `configs/datasets.yaml` 的 `drop_emptied: false` 保留现状，

- **理由（带实测）**：NWPU 650 张正样本在 10 类下**每张都有目标**。

  教它压制真实存在的物体。两种用法的实测规模：

  | `drop_emptied` | 有标注正样本 | 真背景 | 假背景 |
  |---|---|---|---|
  | `false`（当前）| 230 | 150 | **420（含未标注目标）** |
  | `true` | 230 | 150 | 0 |

- **附：类别覆盖实测**（含该类图像数 / 650）：
  baseball_diamond 176 ／ ground_track_field 163 ／ tennis_court 108 ／
  airplane 90 ／ basketball_court 86 ／ vehicle 86 ／ bridge 67 ／ ship 57 ／
  storage_tank 28 ／ harbor 27。

  比当前选择（230/650）高 19 个百分点，**但 baseball_diamond 与命题叙事无关**。
- **备选与放弃原因**：
  - 换成覆盖率最高的 3 类——暂缓。竖线的价值在打通链路，
    3 类足够验证"图→模型→ONNX→ORT"；选型优化留到 D8+。
  - 直接用 10 类——违反 roadmap 硬约束"第一版类别数 ≤3 类"。

## 2026-09-25 · 不为主机代理可用性而关闭 WSL 的网络限制

- **决定**：**保留** Windows 主机的本地代理 `127.0.0.1:7897` 不动；
  WSL 侧走直连（apt 与 PyPI 实测可达）。若将来确需 WSL 访问 GitHub，
  改用 `networkingMode=mirrored`，**而不是关闭代理**。
- **理由（带实测网络矩阵）**：

  | 目标 | WSL 内直连 | Windows 主机 |
  |---|---|---|
  | `archive.ubuntu.com` / `security.ubuntu.com` | ✅ 200 | ✅ |
  | `pypi.org` / `bootstrap.pypa.io` | ✅ 200 | ✅ |
  | `github.com` | ❌ 超时 | ✅（经代理）|

  WSL 在 NAT 模式下访问不到主机的 `127.0.0.1`，启动时明确提示
  *"检测到 localhost 代理配置，但未镜像到 WSL"*。
  但**冒烟测试只依赖 PyPI**，而这条通道本来就是通的——代理不是拦路石。
  反过来，主机访问墙外站点是靠这个代理撑着的，
  **为修 WSL 而关代理，是拿主机的可用性去换一个可选能力，方向反了**。
- **备选与放弃原因**：
  - **关闭主机代理**：否决，损主机且收益仅"WSL 能 clone"一项。
  - **NAT 下把代理指向宿主 IP**（`172.19.176.1:7897`）：否决——
    需代理客户端开"允许局域网连接"，且宿主 IP 每次重启会变，脆弱。
  - **`networkingMode=mirrored`**：保留为按需方案（WSL 2.7.14 支持）。
    未立即启用，因为它要求 `wsl --shutdown` 重启整个 WSL，会打断正在进行的安装。

## 2026-09-25 · ONNX IR version 错配：导出侧必须显式压低

- **决定**：凡本项目产出的 ONNX，都必须显式设置 `ir_version` 不高于目标 onnxruntime 上限；
  `tools/backend_smoke.py` 固定为 **8**（opset 13 要求 IR ≥ 7），并加测试钉住。
- **理由（带实测报错原文）**：

  ```
  onnx        1.23.0   默认写出 ir_version = 14
  onnxruntime 1.23.2   最高支持            = 11
  -> [ONNXRuntimeError] FAIL : Load model failed:
     Unsupported model IR version: 14, max supported IR version: 11
  ```

  `onnx` 与 `onnxruntime` 是两个**独立发版**的包，IR 版本上限并不同步。
  这正是 **D5（导出）→ D6（推理）** 最典型的卡点，而且会在**换环境时突然冒出来**：
  本机 Windows 是 onnxruntime 1.23.2，WSL 里是 **1.30.0**，两者支持的 IR 上限并不相同。
  不显式压低，"导出的模型能不能被读进去"就取决于碰巧装了哪个版本。
- **备选与放弃原因**：不设置、用 onnx 默认值——否决，等于把可复现性交给运气。

## 2026-09-25 · 后端加载失败必须带出底层错误原文

- **决定**：`ORTBackend.load()` 抛 `BackendError` 时必须包含原始异常的类型与消息；
  新增 `tools/backend_smoke.py` 作为**不依赖 torch** 的后端冒烟工具。
- **理由（带实测）**：原实现只报 `加载模型失败：<路径>`，
  把 `Unsupported model IR version: 14` 这类**根因整个吞掉**。
  本次实际发生：冒烟测试失败，第一条报错完全看不出原因，
  须另行手写脚本复现才能定位。
  上板后若遇到算子不支持、opset 过高，同样只会看到"加载模型失败"——**排查方向会被彻底带偏**。
  冒烟工具刻意不依赖 torch：板子上未必装得动 PyTorch，而参考值用 numpy 现算即可。
- **实测效果**：同一模型在 Windows（ORT 1.23.2 / Py 3.10.11）与
  WSL Ubuntu 24.04（ORT 1.30.0 / Py 3.12.3）上均 **PASS，最大绝对误差 0.000e+00**，
  `has_nvidia_components = false`。详见 `docs/env.md` 第 5 节。
- **备选与放弃原因**：只在脚本侧打印异常链（不改后端）——否决，
  后端自身的报错质量是**所有**调用方共享的，不该靠每个调用方自己补救。

## 2026-09-25 · `drop_emptied` 定为 true：宁少勿脏

- **决定**：NWPU VHR-10 在 3 类子集下，**丢弃**"被类别过滤滤空"的 420 张图
  （``configs/datasets.yaml`` 的 ``drop_emptied: true``）。
- **理由**：这 420 张图**画面里确实有目标**，只是属于被排除的 7 类。
  把它们当负样本训练，等于**教检测器压制真实存在的物体**——
  这不是"数据少一点"，而是**标签本身就是错的**。
  数据集规模的实际对比（实测）：

  | `drop_emptied` | 训练可用图 | 其中"假背景" |
  |---|---|---|
  | `false` | 800 | **420（含未标注目标）** |
  | **`true`（选定）** | **380**（230 正 + 150 真背景）| 0 |

  划分后实测：train 304 张（185 正 / 119 背景）、val 76 张（45 正 / 31 背景）。
- **代价（必须记账）**：训练集从 800 降到 380，且正负不平衡（230:150）。
  后续若精度不达标，**第一个要回来检查的就是这个取舍**——
  届时正确的做法是扩大数据集或换许可更干净的数据，而不是把"假背景"加回来。
- **备选与放弃原因**：保留假背景换更大数据量——否决，理由如上。

## 2026-09-25 · 基线检测器选 FCOS + ResNet50-FPN（COCO 预训练）

- **决定**：D3–D4 基线用 ``torchvision`` 的 **FCOS / ResNet50-FPN**，
  加载 COCO 预训练权重、替换检测头为 3 类。
- **理由**：
  1. **无锚框**：后处理只有"解码 + NMS"，没有 anchor 尺寸/长宽比这类需要解释的
     魔法数字。D6 要求"逐框与 PyTorch 对齐"，后处理越简单，
     两侧不一致的来源就越少——差异只可能来自模型本身。
  2. **无 RoIAlign / 两阶段结构**：Faster R-CNN 的 RoIAlign 与 RPN 在 ONNX 导出
     和国产芯片算子支持上都是已知难点。FCOS 是单阶段纯卷积，算子面窄得多。
  3. **许可干净**：torchvision 是 BSD-3，满足"不引入 Ultralytics（AGPL-3.0）"的硬约束。
  4. **必须用预训练**：3 类子集只有 230 张正样本，从零训练不可能收敛。
  实测模型规模：**32.1 M 参数**（可训练 31.8 M）——这是 D8+ 压缩率的**分母**。
- **已知部署风险（留给 D5 验证）**：FCOS 检测头使用 ``GroupNorm``。
  部分推理后端对 GroupNorm 的支持不如 BatchNorm 普遍，**昇腾 CANN 上的算子覆盖必须实测**。
  若不支持，退路是：① 导出前融合/替换 GroupNorm；② 换 RetinaNet（头是 Conv+ReLU，
  本仓库 ``engine/model.py`` 已支持切换）。
  这正是"为部署而设计"的落点，不是杞人忧天。
- **备选与放弃原因**：
  - **Faster R-CNN**：精度通常更好，但两阶段 + RoIAlign 对 D5/D6 是额外风险。保留为候选。
  - **RetinaNet**：算子最保守（头是 Conv+ReLU），若 CANN 不支持 GroupNorm 就切它。
  - **SSD / SSDLite**：最轻，但 torchvision 的 SSD 前向里后处理耦合较深，导出更麻烦。
  - **自研网络**：可控性最高，但 D3–D4 的目标是打通链路而非刷精度，不划算。

## 2026-09-25 · `num_classes` 口径：torchvision 要"含背景"，且它自己的文档自相矛盾

- **决定**：``build_detector(name, num_classes)`` 的 ``num_classes`` 一律指
  **前景类别数**，由本函数在内部 ``+1`` 转成 torchvision 要的含背景口径；
  调用方不要自己加。
- **理由（带实测报错）**：本项目实际踩到，症状极具误导性：

  ```
  CUDA error: device-side assert triggered
  aten/src/ATen/native/cuda/IndexKernel.cu:111:
      Assertion `-sizes[i] <= index && index < sizes[i]` failed
  # 报错栈指向 fcos.py:98  generalized_box_iou_loss(pred_boxes[foreground_mask], ...)
  ```

  报错位置（GIoU loss）**离真正原因很远**。真因在 fcos.py:90::

      gt_classes_targets = torch.zeros_like(cls_logits)   # 最后一维 = num_classes
      gt_classes_targets[foreground_mask, gt_classes[foreground_mask]] = 1.0

  FCOS 把**标签值直接当作分类头最后一维的下标**。标签是 1/2/3，
  而 ``num_classes`` 传了 3 → ``[..., 3]`` 在长度为 3 的维度上越界。

  而 torchvision 的两处 docstring **互相矛盾**，正是这个坑难查的原因：

  | 位置 | 原文 | 含义 |
  |---|---|---|
  | ``fcos_resnet50_fpn`` | "number of output classes of the model (**including the background**)" | 含背景 |
  | ``FCOSClassificationHead`` | "number of classes to be predicted" | 不提背景 |

  正确口径是**含背景**（COCO 用 91 = 80 + 1）。本仓库改为在
  ``build_detector`` 内部统一 ``+1``，并用**真实前向**测试钉死
  （``tests/test_engine.py::test_detector_forward_accepts_labels_starting_at_one``）。
- **备选与放弃原因**：让每个调用点自己 ``+1``——否决，等于每个调用点都有一次错的机会。

## 2026-09-25 · NWPU VHR-10 无官方划分，本项目自定固定种子划分

- **决定**：用 ``split_samples(val_ratio=0.2, seed=20260925)`` 划分，种子写进配置文件。
- **理由**：
  1. NWPU VHR-10 **没有官方 train/test 划分**，必须自定；
  2. 用固定种子而非每次随机洗牌：否则每次的验证集都不同，
     `docs/decisions.md` 要求的"消融实验可对照"就无从谈起；
  3. 划分前按 ``image_id`` 排序，使划分**与输入顺序无关**
     （样本从多源汇总时顺序可能不稳定）。该性质已有测试覆盖。
- **⚠️ 由此产生的一条硬性引用纪律**：**我们的 mAP 不能与文献数字直接比较**——
  划分不同、训练集大小不同、类别数不同。本项目的数字只能用于**内部对照**
  （如压缩前后、不同骨干之间）。报告里引用时必须写明这一点。
- **备选与放弃原因**：随机划分（不固定种子）——否决，不可复现即不可信。

## 2026-09-25 · D3–D4 基线训练完成：配方与结果（含两条必须一起引用的限定）

- **决定**：基线以 `configs/train_baseline.yaml` 为准并已完成训练，
  权重登记在 `artifacts/README.md`（含 SHA256），后续一切"优化后"的数字都与它对比。
- **配方（复现所需全部信息）**：
  - 数据：NWPU VHR-10，3 类，`drop_emptied: true` → 380 张；划分后 train 304 / val 76
  - 模型：FCOS + ResNet50-FPN，COCO 预训练后换检测头，**32.1 M 参数**
  - 优化：20 轮 / bs 4 / SGD lr 0.005（12、18 轮各降 10 倍）/ warmup 200 it / 梯度裁剪 10
  - 实测耗时：**686.9 s（11.4 min）**，平均 34.3 s/轮（RTX 5060 Laptop）
- **结果（实测）**：

  | 指标 | 值 |
  |---|---|
  | train total loss | 2.7300 → **0.7311** |
  | val total loss | 4.0773 → **0.6278**（最低 0.6183，出现在第 13 轮）|
  | 末轮 loss 分量 | classification 0.0149 / bbox_regression 0.1144 / bbox_ctrness 0.6018 |

  验证集上按 IoU@0.5 贪心匹配（阈值 0.5）：召回 **0.978**、精度 **0.952**，
  正样本图出框 330 个（标注 321 个）；**31 张纯背景图合计只出 1 个框**。
  阈值 0.7 时背景图出框为 **0 个**。

- **⚠️ 限定一：这不是 mAP，不能当 mAP 报。**
  上述匹配是"贪心 IoU@0.5 一对一"，不是 COCO 的 mAP@[.5:.95]，
  也不是 pycocotools 口径。正式精度评测属 D6+ 的 `scripts/eval.py`。
  另外验证集只有 45 张含目标图 / 321 个框，**置信区间很宽**，
  小数点后第二位没有意义。

- **⚠️ 限定二：已排查"近似重复场景泄漏"，但排查不彻底。**
  "随机划分把重复场景分到两侧从而导致精度虚高"是本项目主动怀疑并验证过的一件事：
  用 32×32 灰度归一化互相关，取每张 val 图在 train 中的最近邻，实测

  | 相似度阈值 | val 中超过阈值的图 |
  |---|---|
  | ≥ 0.99 / 0.95 / 0.90 / 0.80 | **0 / 76（四项全为 0）** |
  | 相似度分布 | 中位 0.278，均值 0.314，最大 0.700 |

  结论：**不存在近似重复的整图**，该怀疑被证伪。
  **但**整图相关性查不出"同一机场、不同裁剪"这类场景级重叠——
  所以"精度偏高"仍有一个未被排除的解释。加之 NWPU 的目标（停机坪上的飞机）
  大而清晰，本身就不是困难任务，高数字符合预期。
  → 报告引用时**必须同时写明本段**，不能只报 0.978/0.952。

- **备选与放弃原因**：把 val 结果当"模型能力"直接写进材料——否决。
  上面两条限定不写清楚，评委一问"你这是 mAP 吗""划分会不会泄漏"就答不上来，
  而这两问几乎必问。
